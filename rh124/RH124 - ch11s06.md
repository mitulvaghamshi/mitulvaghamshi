# Guided Exercise: Manage Default Permissions and Special Permissions

Control the default permissions of user-created files, and explain special permissions on files.\
**Outcomes**

- Create a shared directory where the operators group automatically owns new files.
- Configure the directory so that only the file owner (and the root user) can delete files.
- Temporarily change the umask setting.\
  As the student user on the workstation machine, run the following lab command to prepare your environment for this exercise, and to ensure that all required resources are available:

```
student@workstation:~$ lab start perms-default
```

**Instructions**\
In this guided exercise, the umask setting has been set to 0007, which is different from the default 0022. This setting change enables you to inspect the permissions set for new files and directories.

1. Log in to the servera system as the operator1 user.student@workstation:~$ **ssh operator1@servera**
2. ...output omitted...
3. [operator1@servera ~]$
4. Create the /tmp/operators directory and change its owning group to operators. Verify the new group ownership.
   1. Create the /tmp/operators directory.[operator1@servera ~]$ **mkdir /tmp/operators**
   2. Change the group ownership of the /tmp/operators directory to the operators group.[operator1@servera ~]$ **chown :operators /tmp/operators/**
   3. Verify that the group ownership of /tmp/operators/ is applied correctly.[operator1@servera ~]$ **ls -ld /tmp/operators/**
   4. drwxrwx---. 2 operator1 operators 6 Jun 4 03:24 /tmp/operators/
5. Verify the operator1 user's default umask value, and list the permissions of the /tmp/operators directory.
   1. List the operator1 user's default umask value.[operator1@servera ~]$ **umask**
   2. 0007This umask setting grants all user and group permissions, and prevents others from having any permissions on new files or directories.
   3. Verify that the permissions of the /tmp/operators directory are consistent with the 0007 umask value.[operator1@servera ~]$ **ls -ld /tmp/operators/**
   4. drwxrwx---. 2 operator1 operators 6 Jun 4 03:24 /tmp/operators/The rwxrwx--- permissions set matches the umask rule.
6. Ensure that files created in the /tmp/operators directory are owned by the operators group. Then, verify the ownership.
   1. Use symbolic notation to configure the setgid special permission on the /tmp/operators directory to make the operators group the group owner of new files.[operator1@servera ~]$ **chmod g+s /tmp/operators/**
   2. Verify that you have correctly set the setgid permission on the /tmp/operators directory.[operator1@servera ~]$ **ls -ld /tmp/operators/**
   3. drwxrws---. 2 operator1 operators 6 Jun 4 03:24 /tmp/operators/
7. Ensure that users with write access to the /tmp/operators directory can remove only files that they own. Then, verify the change.
   1. Use the octal method to configure the sticky bit on the /tmp/operators directory and preserve the existing permissions. The current permission mode is 2770 (drwxrws---).[operator1@servera ~]$ **chmod 3770 /tmp/operators/**
   2. Verify that you have correctly applied the sticky bit to the /tmp/operators directory.[operator1@servera ~]$ **ls -ld /tmp/operators/**
   3. drwxrws--T. 2 operator1 operators 6 Jun 4 03:24 /tmp/operators/
8. Create a file named ops_file1.txt in the /tmp/operators/ directory. List the ownership and permissions of the ops_file1.txt file.
   1. Create a file named ops_file1.txt in the /tmp/operators/ directory.[operator1@servera ~]$ **touch /tmp/operators/ops_file1.txt**
   2. Change to the /tmp/operators/ directory. List the ownership and permissions of the ops_file1.txt file.[operator1@servera ~]$ **cd /tmp/operators/**
   3. [operator1@servera operators]$ **ls -l ops_file1.txt**
   4. -rw-rw----. 1 operator1 operators 0 Jun 4 03:28 ops_file1.txt
9. Temporarily change the umask to 0022 for the operator1 user. Create a second file named ops_file2.txt in the /tmp/operators/ directory. Then, list the ownership and permissions of both the ops_file1.txt and ops_file2.txt files.
   1. Change the umask to 0022 for the operator1 user.[operator1@servera operators]$ **umask 0022**This umask setting allows the user to read and write new files, but the group and others can only read those files.
   2. Create a file named ops_file2.txt in the /tmp/operators/ directory.[operator1@servera operators]$ **touch ops_file2.txt**
   3. List the ownership and permissions of both the ops_file1.txt and ops_file2.txt files.[operator1@servera operators]$ **ls -l ops_file{1,2}.txt**
   4. -rw-rw----. 1 operator1 operators 0 Jun 4 03:28 ops_file1.txt
   5. -rw-r--r--. 1 operator1 operators 0 Jun 4 03:34 ops_file2.txtThe permissions on the ops_file2.txt file match the permissions from the 0022 umask setting. The ops_file1.txt file maintains the previous permissions because the file was created before the umask change.
10. Log in as the operator2 user and attempt to delete a file created by the operator1 user. You should not be able to delete the ops_file1.txt file as the operator2 user because the /tmp/operators/ directory is configured with the sticky bit permission.
    1. Switch to the operator2 user. Use redhat as the password.[operator1@servera operators]$ **su - operator2**
    2. Password: redhat
    3. ...output omitted...
    4. [operator2@servera ~]$
    5. Attempt to delete the /tmp/operators/ops_file1.txt file, which was created by the operator1 user.[operator2@servera ~]$ **rm /tmp/operators/ops_file1.txt**
    6. rm: cannot remove '/tmp/operators/ops_file1.txt': Operation not permittedAs expected, the remove operation fails, because the sticky bit permission prevents users from deleting files owned by other users.
